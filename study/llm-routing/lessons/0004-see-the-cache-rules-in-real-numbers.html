The lab

The script assets/cache_lab.py builds one conversation of about 4,000 tokens on Claude Sonnet 5.5:

  • four weather tools, about 1,500 tokens,
  • a system prompt, about 2,000 tokens,
  • four turns of history, about 450 tokens.

It puts a cache breakpoint at the end of each part. Then it sends that conversation eight more times, each with one routing move applied, and prints the cache numbers from every response.

tools ≈1,500
system ≈2,000
history ≈450
new turn

Three breakpoints, one at the end of each segment. Each one can hold its own cache entry.

Three details keep the lab cheap and honest:

  • max_tokens: 0. The API reads the prompt, writes the cache, and returns a full usage block. No output tokens are billed.1
  • Sonnet, not Haiku, for the main conversation. Haiku 4.5 caches nothing under 4,096 tokens. Sonnet 5.5 caches from 512, so each segment here is big enough to get its own cache entry.1
  • A random run id at the front of the tools. Each run starts cold instead of reading what the last run cached. That's the timestamp mistake from lesson 2's warm-up, used on purpose.

Step 1: predict, before you run anything

Answer all eight. The quiz tells you what the rule predicts, and the script will tell you whether the API agrees. Every step starts from the warm conversation, not from the step before it.

1. Same conversation, a different new user turn appended.

The last breakpoint sits on the last history block, before the new turn, so the whole prefix is read. This step's read count becomes the 100% that every later step is compared with.

2. Set tool_choice to none.

A tool_choice change only invalidates messages.1 Expect a read of tools plus system, around 85–90% of step 1, and a small write for the history.

3. Add one sentence to the end of the top-level system prompt.

Only the tools entry survives. Expect a read of about 35–40% of step 1, and a write of the system prompt plus the history.

4. Leave system alone, and append the same sentence as a {"role": "system"} message after the history.

Same instruction as step 3, but appended after the cached prefix instead of edited into it. Sonnet 5.5 supports this.1 Expect about 100%. Compare steps 3 and 4 side by side when the numbers come back: this pair is lesson 1 in miniature.

5. Add one sentence to the last tool's description.

Tools are the leftmost segment. Expect a read of 0, and the whole prompt written again.

6a. A separate Haiku classifier request with a one-line prompt. What does its own cache do?

There is nothing to hit. The prompt is far below any minimum cacheable length, so expect write 0 and read 0. The docs say exactly this: when both are 0, nothing was cached.1 A real classifier prompt with categories and examples would need to clear the minimum to cache.

6b. Right after that classifier call, the main conversation gets its next turn.

The classifier ran on another model with another prompt. It never touched this conversation's prefix. Expect about 100%.

7. The same request, byte for byte, sent to Opus 5.5.

The cache belongs to Sonnet. Expect read 0, and the whole prompt written on Opus at Opus's write price.1

Step 2: run it

From the repo root, with your API key in the environment:

ANTHROPIC_API_KEY=sk-ant-... uv run --no-project study/llm-routing/assets/cache_lab.py

uv fetches the anthropic SDK for this one run, so nothing gets installed in the workspace. The script makes nine requests and prints one row per request.

Step 3: read the table

ColumnMeaning
writecache_creation_input_tokens: tokens written to cache on this request, billed at 1.25x base input.
readcache_read_input_tokens: tokens served from cache, billed at a small fraction of base input.
freshinput_tokens: tokens after the last breakpoint, processed and billed normally. Mostly the new turn.
read %This step's read compared with step 1's. It shows how much of the prefix survived the move.
