Every routing decision is a cache decision

One rule tells you whether a router keeps or throws away your prompt cache.

Your win: by the end of this page, you can look at any routing move and predict whether the Claude prompt cache survives it, and if not, where it breaks. Takes about 15 minutes.

What a router does

Anthropic defines routing as a pattern that "classifies an input and directs it to a specialized followup task".1 The followup can be a different prompt, a different set of tools, or a different model. Their two examples are exactly the two kinds in your mission: sending refund requests and tech-support questions to different prompts and tools (intent routing), and sending easy questions to Haiku and hard ones to Sonnet (model routing).1

Every one of those followups changes something about the next request. The prompt cache is keyed on exactly those things. So the router and the cache are always in tension, and this lesson is about that tension.

What the cache is keyed on

A prompt cache stores the model's computed state for the unchanged tokens at the start of a prompt, so a later request with the same prefix can skip reprocessing them.3 On the Claude API, a cache hit needs three things to match:

  1. The workspace. Caches are isolated per workspace on the Claude API.2
  2. The model. The cached state comes out of one model's weights, so a different model cannot read it. Switching models always starts cold.
  3. The exact prefix, in order. The prefix is built as tools, then system, then messages.2 One changed token invalidates everything after it.4

Here is the rule to keep: a change invalidates its own segment and every segment to its right. Anthropic's invalidation table says it directly: "Changes at each level invalidate that level and all subsequent levels."2

tools
system (edited)
messages (turns 1…n)
new turn

Edit the system prompt and the tools cache survives, but system and every message after it must be reprocessed.

Two exceptions worth knowing

  • tool_choice only breaks the messages segment. Changing it leaves the tools and system caches valid.2
  • Appending is not editing. On models that support it, you can add new instructions partway through by appending a {"role": "system"} message to messages rather than editing the top-level system field. The cached prefix stays unchanged.2

Why it is worth caring

Cache reads cost 0.1x the base input price on most Claude models, and 5-minute cache writes cost 1.25x.2 Manus, which runs agents at about 100 input tokens per output token, calls KV-cache hit rate "the single most important metric for a production-stage AI agent".4 A router that breaks the cache at turn 30 makes you pay for all 30 turns again, at the higher write price.

Practice: predict the damage

Each scenario is a conversation on Claude Sonnet that has been running for a while, with a warm cache. The router does one thing before the next request. Pick what happens to that conversation's cache.

1. The router decides this turn is about hiking and replaces the top-level system prompt with a "hiking specialist" persona. Same model, same tools.

Editing system breaks the system segment and everything to its right. The tools cache, which sits to its left, survives. This is the most common way intent routing breaks a cache without anyone noticing.

2. Before each turn, the app makes a separate Haiku call with a fixed classifier prompt to pick a route. The main Sonnet conversation then gets only the new user turn appended.

The classifier is its own request, with its own prefix, on its own model. The main conversation's prefix is untouched. One catch for the classifier itself: Haiku 4.5 won't cache any prompt shorter than 4,096 tokens, so a short classifier prompt is never cached at all.2

3. The router forces the model to call get_forecast on this turn by setting tool_choice. Nothing else changes.

This is one of the two exceptions. A tool_choice change invalidates only the messages segment. In a long conversation, the messages segment is most of the tokens, so this still costs real money.2

4. At turn 12, the router judges the question hard and sends the same history, tools, and system prompt to Opus instead of Sonnet.

The prefix is byte-for-byte identical, but the cache belongs to Sonnet. Opus has no state for it, so it reprocesses all 12 turns and pays the cache write price on top. Per-turn model routing in a long conversation is the most expensive move on this page.

5. On a model that supports it, the router appends a {"role": "system"} message to messages: "Answer as the hiking specialist."

This is the same intent as scenario 1 with the opposite outcome. The instruction is appended after the cached prefix instead of edited into it, so only the new block is fresh input.2

6. The router adds two specialist tools to the tools array for this turn only, then removes them next turn.

tools is the leftmost segment, so any change there invalidates everything.2 Removing them next turn breaks it again. Manus hit this and stopped adding or removing tools mid-task. They keep every tool defined and restrict which ones the model may pick instead.4

What this means for router design

Compare scenarios 1 and 5, and scenarios 2 and 4. Three habits follow from the rule:

  • Route in a separate request. A classifier call doesn't touch the conversation it routes.
  • Put per-route variation at the end, not the front. Append instructions. Don't edit tools or system.
  • Pick the model at a boundary. Choose it when a conversation or a delegated task starts, not on every turn.

The third habit raises the next question. If a hard subtask needs Opus, where does that call go so it doesn't wreck the main conversation's cache? That is what lesson 2 covers: the layers where routing can live.
