Router design

Building and testing an application-layer router. Checked against the sources on 12 October 2026.

First: do you need one?

Route only when inputs fall into distinct categories, the classification can be done accurately, and a router beats one prompt on your evals.

Pick the shape

ShapeUse whenCostCache note
Route before answering (RouteLLM)You can judge difficulty from the question, but not cheaply check the answerOne classifier call per requestDecides once. Do it at a conversation or task boundary
Cascade (FrugalGPT)An automatic check on the answer exists (schema, tests, validator)A second full call on each escalationEach escalation is a cold cache on the next model. Best for short, independent requests

Classifier checklist

  • Write category definitions with the boundary between neighbours spelled out.
  • Prompt: reasoning in <reasoning>, then one label in <intent>, plus a few examples.
  • Model: Haiku at low effort for simple, high-volume routing. Sonnet for many categories or deep expertise.
  • Many classes: a top-level classifier, then a sub-classifier per group.
  • Keep the classifier prompt fixed, so its own prefix can cache (check the model's minimum cacheable length).
  • Model routers: tune the threshold to your cost target. It sets how borderline questions are routed.

Evaluation

Router typeMeasureBaseline
Intent routerAccuracy on a labelled set, cost per classification, response time, accuracy on a separate edge-case setThresholds set before testing (the guide's examples: 95% overall, 80% on edge cases)
Model routerQuality recovered at a given share of strong-model calls (RouteLLM: APGR, CPT)A random router at the same share, which recovers about that share of the quality gap

Red flags

  • Quality reported without cost, for a model router.
  • A test set with no ambiguous cases.
  • Misroutes fixed by upgrading the model before sharpening the categories.
  • A cascade escalating deep inside long conversations.
