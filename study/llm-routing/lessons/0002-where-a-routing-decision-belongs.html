Where a routing decision belongs

Three layers can route a request. Each one sees different information, and each one can break your cache.

Your win: given a routing decision, you can name the layer that should own it, and say what that layer has to keep sticky so the prompt cache survives. Takes about 15 minutes.

W1. The app writes the current time, to the second, into the top-level system prompt on every request.

The system segment changes on every request, so it and everything to its right are reprocessed every time. Manus calls this the classic cache-killing mistake.4

tools is the leftmost segment. Any edit there, even to a description, invalidates everything.5

Adding or removing images anywhere in the prompt invalidates the messages segment. Tools and system survive. Lesson 1 didn't cover this one, but the rule plus the reference table did.5

Three layers, three questions

A request passes through up to three places that can route it. They answer different questions, because each one sees different information.

ApplicationWhat kind of task is this, and who handles it? Your code or your orchestrator agent. It is the only layer that sees what the user means, the conversation, and the task state.
GatewayWhich deployment serves this model name right now? A proxy such as LiteLLM or OpenRouter. It sees model names, provider health, rate limits, and prices. It doesn't know what the task is.
ServerWhich machine already holds this prefix? The inference server and the load balancer in front of its replicas. It sees KV cache state and GPU load.

Top to bottom: from closest to the user to closest to the GPU.

Here is the placement rule: give each decision to the layer that has the information it needs. Intent needs meaning, so it belongs in the application. Failover needs provider health, so it belongs in the gateway. Machine choice needs cache state, so it belongs in the server layer. A decision made in the wrong layer is made blind.

Application: intent, and model choice at a boundary

Lesson 1 ended on a question: if a hard subtask needs a stronger model, where does that call go? Anthropic's Research system answers it. A lead agent on Claude Opus hands subtasks to subagents on Claude Sonnet, and each subagent runs "with their own context windows".1 The model is chosen when the subtask is delegated, so the lead conversation never changes model and keeps its cache. The cost: multi-agent runs used about 15 times the tokens of a chat.1

Gateway: deployments, fallbacks, and the shuffle trap

LiteLLM's default strategy, simple-shuffle, spreads requests for one model name across all its deployments.2 For a conversation, that is a cache problem. LiteLLM's own docs say to pin a session "when the deployments behind a model group do not share state, for example provider-side prompt caching", and they provide a session_affinity check for it.2 OpenRouter does the same thing by default. It keeps a conversation on the same provider for as long as caching pays, until 10 minutes of inactivity, keyed on an optional session_id.3

Server: send the request to the cache

A KV cache lives in one server's memory. vLLM's automatic prefix caching reuses it across turns of a conversation on that instance.6 With several replicas, a plain load balancer scatters turns across them. The Kubernetes Gateway API Inference Extension adds an endpoint picker that routes on metrics such as "Prefix Cache status".7 On the Claude API, Anthropic runs this layer, not you. Your only lever there is the stable prefix from lesson 1.

The cache rule across layers: every layer has to keep a conversation on whatever holds its cache. The application keeps the same model. The gateway keeps the same deployment. The server layer keeps the same machine. Each one fails the same way: it routes for spread or for cost on each turn, and forgets the conversation.

Practice: name the layer

For each case, pick the layer that should own the decision, or the layer that is causing the problem.

1. Midway through a Sonnet conversation, the lead agent judges one subtask hard enough to need Opus.

Only the application knows the subtask is hard. The cache-safe way is the Research system's: delegate to a subagent with its own context on Opus, and keep the lead conversation on Sonnet.1

2. A team routes through LiteLLM with simple-shuffle across two Azure regions. Each conversation's cache hit rate hovers around half. Which layer is losing it?

The shuffle sends turns of one conversation to two deployments that don't share a cache. The fix lives in the same layer: turn on session_affinity and send a session id on every turn.2

3. You self-host a model on four vLLM replicas. You want each turn to land on the replica that already holds that conversation's prefix.

Only the serving side knows which replica holds which prefix. That is what the Inference Extension's endpoint picker reads.7 The application could pin turns by session id as a crude version, but it can't see cache eviction or GPU load.

4. Refund questions should go to a refund agent with its own prompt and tools. Shipping questions should go to a shipping agent.

This is Anthropic's textbook routing example, and it needs to know what the user means.8 A gateway sees a model name, not a refund.

5. vLLM replicas sit behind a round-robin load balancer. Prefix caching is on, yet multi-turn hit rates are poor.

Each replica caches only what it has seen.6 Round robin sends turn 2 to a replica that never saw turn 1. Manus gives the same advice for self-hosted vLLM: route requests consistently across workers, using session ids.4

6. The Anthropic API is overloaded. You want the same model served from another platform until it recovers.

Failover needs provider health, which is what gateways track: fallbacks, cooldowns, and retries are LiteLLM's core features.2 Expect the first request on the new platform to start cold, since caches don't move between providers.

What to take away

  • Meaning-based routing stays in your code. Intent, task difficulty, and which agent handles what.
  • Infrastructure routing stays below it. Providers, regions, and replicas.
  • Every layer needs stickiness. Same model, same deployment, same machine, for the life of a conversation.
