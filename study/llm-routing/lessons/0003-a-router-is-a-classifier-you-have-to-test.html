A router is a classifier you have to test

How to build an application-layer router, and how to tell if it beats picking at random.

Your win: you can pick the right shape of router for a job, say what to fix when it misroutes, and judge it against the baseline it has to beat. Takes about 15 minutes.

Warm-up: lessons 1 and 2, from memory

W1. You pass a session_id on every turn so a conversation stays on one provider. Which layer reads it?

OpenRouter and LiteLLM both use a session id to pin a conversation to one provider or deployment, so its cache stays warm.6

W2. A Sonnet lead agent hands a hard subtask to a new Opus subagent with its own context. What happens to the lead conversation's cache?

The subagent is a separate conversation. The lead's model and prefix don't change, so its cache survives. This is how you route to a stronger model at a boundary.

W3. A gateway's automatic model router picks a different model on turn 7 of a conversation.

A new model has no cache for this conversation. OpenRouter's docs warn about exactly this: its Auto Router reuses the earlier model only "on a best-effort basis".6

Two shapes of model router

Route before answeringCascade
HowA cheap classifier picks a model, then that model answers once.The cheap model answers. A check decides if the answer is reliable. If not, the next model tries.
Known fromRouteLLM3FrugalGPT4
NeedsA way to predict difficulty from the question aloneA cheap way to check an answer after it exists
CostOne classifier call on every requestPaying twice whenever it escalates

The choice comes down to one question: is it easier to judge the question or the answer? If an answer can be checked automatically, for example it must pass a JSON schema or a test, a cascade only escalates when it has to. If the answer is a judgement call nobody can cheaply check, you have to predict difficulty up front.

A cascade has a cost lesson 1 predicts. An escalation sends the whole context to a second model, which has no cache for it. On a short single query that's cheap. Deep into a long conversation, every escalation pays for the full history again.

Build the classifier well

Anthropic's ticket-routing guide is the most practical source here.2 Four points carry most of the weight:

  • Categories first. Claude's routing accuracy is "directly proportional to how well-defined your system's categories are".2 Fix fuzzy categories before you reach for a bigger model.
  • Reasoning, then label. The guide's prompt asks for reasoning in <reasoning> tags, then one label in <intent>, with a few examples.2
  • Smallest model that passes. Haiku at low effort suits simple, high-volume classification. Move to Sonnet for many categories or deep domain knowledge.2
  • Many classes, split the tree. A top-level classifier picks a broad group, and each group has its own sub-classifier.2

For model routing, RouteLLM turns the router's output into a decision with a threshold. The router estimates how likely the strong model is to win, and the threshold sets how sure it must be before paying for the strong model. Moving the threshold trades cost for quality.3 The threshold is where you decide what borderline questions cost you.

Test it against the right baseline

A router that sends everything to the strong model gets perfect quality and saves nothing. So quality alone says nothing about a model router.3 RouteLLM measures quality at a given share of strong-model calls and compares it with a random router at the same share.3

Why random is the bar. A random router that sends 40% of questions to the strong model recovers, on average, about 40% of the quality gap between the two models. A router is worth its classifier call only if it recovers much more than that at the same cost. In RouteLLM's own tests, two of their classifiers performed "close to random" until they were given better training data.3

For intent routing, Anthropic's guide measures three things on a labelled test set, against thresholds you set before you start:2

  • Accuracy, for example 95% out of 100 tests.
  • Cost per classification.
  • Response time.

The guide also says to keep a separate edge-case set and aim for at least 80% on it.2

Finally, check whether you need a router at all. Anthropic's advice is to add complexity "only when it demonstrably improves outcomes".1 If one prompt already passes your evals, a router only adds a call that can be wrong.

Practice: design and judge

1. An agent turns requests into tool-call arguments that must pass a JSON schema. Most requests are easy. Which shape fits?

The schema is a free, automatic check on the answer. Let the cheap model try and escalate only on a failed check. That is FrugalGPT's pattern: later models are called only when the earlier answer is "deemed insufficiently reliable".4

2. A Haiku classifier with routes forecast, travel, and other keeps mixing up forecast and travel questions. What do you fix first?

Confusion between two specific routes points at their definitions. Accuracy tracks how well-defined the categories are.2 Write the boundary down, with an example on each side. A bigger model would only guess better at a line you never drew.

3. Your model router sends 60% of questions to the strong model and recovers 60% of the quality gap between the two models. Is it earning its keep?

A random router at 60% strong calls recovers about 60% of the gap on average. Yours costs the same and recovers the same, plus a classifier call on every request. It's doing nothing.3

4. A cascade runs each turn on Haiku and escalates to Sonnet when a check fails. The first escalation happens at turn 25. What does the Sonnet call find in its cache?

Sonnet has never seen this conversation, so all 25 turns are new input at the cache-write price.5 Cascades are cheapest on short, independent requests. In long conversations, choose the model at a boundary.

5. Your intent router scores 98% on 100 labelled test cases. All of them are clear, typical requests. What's missing before you trust it?

Clear cases are where every router does well. Anthropic's guide keeps a separate edge-case set with its own target of at least 80%.2 The ambiguous requests are the ones a router exists to handle.

6. Users ask for travel advice. Difficulty varies a lot, and nothing can cheaply check whether an answer is good. Which shape fits?

A cascade needs an answer check, and there isn't one. Predict difficulty from the question, RouteLLM style, and tune the threshold to your budget.3 "Always use strong" is the fallback if the router can't beat random.

7. One prompt already handles all three question types at 96% on your evals. A teammate wants to add an intent router with one specialist prompt per type.

A router adds a call, latency, and a new way to fail. Add it only when it "demonstrably improves outcomes".1 If the eval later shows one type dragging the score down, revisit it then.

What to take away

  • Pick the shape by what you can judge. If you can check the answer, cascade. If you can only judge the question, route before answering.
  • Fix categories before models. Sharp boundaries, reasoning before the label, and the smallest model that passes.
  • Beat random at equal cost, or remove the router. Test quality and cost together, on a separate edge-case set too.
